03 — Under the hood

Real FFmpeg. Real flags. No abstraction tax.

Vortex doesn't wrap a proprietary transcoding API and call it a day. It ships the actual FFmpeg binary compiled to WebAssembly and drives it with the same command-line flags you'd type in a terminal.

  • Multi-threaded when it can be. If the page is cross-origin isolated, the threaded core loads and every available CPU core gets used.
  • Graceful single-thread fallback. Deployed without COOP/COEP headers? It switches to the ESM core instead of breaking.
  • Stream copy by default. Every engine that can avoid re-encoding does, because re-encoding is where quality and time both go to die.
  • Live engine log. Every line FFmpeg emits is streamed to the inspector, so you can see exactly what ran and why.

06 — Questions

The things people ask first.

Are my files really never uploaded?
Correct. The page loads FFmpeg compiled to WebAssembly, and your file is read into the browser's own memory through the File API. The only network requests this app makes are the initial downloads of the FFmpeg core and the fonts. Once the engine lamp reads READY, you can disconnect from the internet entirely and every tool keeps working.
Is it genuinely free? What's the catch?
No catch and no account. There is no server doing the work, so there is no compute bill to pass on to you — that is the whole architectural point. No credits, no watermarks, no export limits, no upsell.
Why does the first load take a few seconds?
The browser is downloading the FFmpeg WebAssembly core — roughly 25–30 MB depending on whether the multi-threaded build is available. That happens once and is cached from then on. The status line at the bottom of the studio tells you exactly which core loaded.
What's the maximum file size I can process?
There's no application-level limit, but everything lives in memory, so the practical ceiling is your available RAM — and browsers cap a single tab's heap well below your total. As a rule of thumb, keep inputs under a couple of gigabytes. Lossless stream-copy operations (mux, trim, mute, sync) are dramatically lighter than re-encoding ones.
Does it work on my phone?
The interface is fully responsive and the engines do run, but mobile browsers enforce much tighter memory ceilings and are slower at WebAssembly. Short clips and audio-only jobs are fine; a multi-gigabyte video is not a good idea on a phone.
Why do some operations finish instantly and others take minutes?
Stream copy versus re-encode. Trimming, muting, muxing and sync-shifting only rearrange existing packets, so they run at hundreds of times real-time. Compression, re-framing and GIF rendering have to decode and re-encode every single frame — genuinely expensive work, and the same work a desktop editor would be doing.

Your file never leaves this tab. It's read into browser memory, processed by WebAssembly, and written back to your disk. There is no server on the other end of this.

Getting the best results

  • Prefer the stream-copy engines — mux, trim, mute, sync. They finish in seconds with zero quality loss.
  • Re-encoding engines (compress, reframe, GIF) scale with clip length. Keep the tab open and let them run.
  • Probe first if an engine errors — the inspector reveals the actual container and codec.
